# ATM 出钞指令层安全设计

> 针对"撬开机柜、把电脑接到出钞模块数据线上直接发指令吐钞"的黑盒攻击，用 Java 重写
> 业务软件 ↔ 出钞模块 之间的指令层。

## 1. 我们要防什么

原始事故里，攻击者的能力是：**物理接触出钞模块的数据总线**。由此可以推导出四类必须分别
应对的威胁，任何一类漏掉，整条防线都会被绕过：

| # | 攻击 | 攻击者拥有的东西 | 防线落点 |
|---|------|------------------|----------|
| T1 | **总线直接注入**：自制电脑挂在数据线上，按协议发"出钞"指令 | 总线读写、协议格式 | 模块只认**主机签名**，不认总线上的任何自称 |
| T2 | **替换业务软件电脑**：整台 PC 换成攻击者的，仍自称原终端 | 终端全部代码与密钥、终端身份 | 终端根本不持有能授权出钞的私钥；授权私钥只在主机 HSM 里 |
| T3 | **模块替换 / 维修重配对**：换一个模块，或诱骗/强迫重配对 | 物理拆装、可能拿到旧模块 | 重配对需 **主机签发的配对授权 + 物理维修跳线 + 一次性授权**，且抬升 epoch |
| T4 | **离线套现**：断网时反复出钞，或用编程器回滚模块存储"刷新额度" | 断网、芯片级读改写 | 主机预签**绝对累计上限**信封，模块用 **OTP 锚定的单调累计计数** 判定 |

一个贯穿始终的原则：**信任根在主机，不在终端，也不在总线上的任何消息**。终端即使被完全
控制，也只能让 ATM 失败，不能让它出钞。

## 2. 核心机制

### 2.1 主机签名授权（在线）——整个方案的心脏

每笔出钞都必须携带主机 HSM 用**出钞授权私钥**签名的 `HostAuthorization`。签名覆盖且仅覆盖
以下字段，任何一项被改动都会导致验签失败：

```
version | moduleId | terminalId | txId | amountCents | CashPlan(逐面额张数)
        | nonce | channelBinding | seq | issuedAt | expiresAt | keyEpoch
```

逐个字段为什么必须在签名里：

- **moduleId / terminalId**：授权绑定到"这一个模块 + 这一台终端"，A 机的授权无法在 B 机用。
- **amountCents 且必须等于 CashPlan 总额**：不止签总额，连**精确的钞票计划**也签。否则终端
  可把"主机批准 2 张 100"改成"100 张 10 元"仍满足总额。
- **nonce**：模块每次会话产生的 32 字节一次性挑战。终端必须先取出挑战再去主机换签名，模块
  用后即弃 → 抓包重放无效（T1）。
- **channelBinding**：由当前链路会话密钥派生。授权被绑定到"这一次 TLS 级会话"，跨会话重放
  立即失效。
- **seq**：主机为每个模块单调递增分配。模块持久化高水位（OTP 锚定），必须严格增大且跳跃有上限。
- **issuedAt / expiresAt**：短有效期，限制被劫持授权的可用窗口。
- **keyEpoch**：当前配对轮次。重配对抬升 epoch → 旧 epoch 的所有授权作废（T3）。

签名用 **Ed25519**：出钞模块只需持**公钥**，即使被拆走也拿不到签名能力；验签在弱芯片上开销小。

### 2.2 链路层：临时 X25519 + AES-GCM

- 双方每会话生成**临时** X25519 密钥对，HKDF 派生出**方向分离**的两把会话密钥。
- 出钞模块在第一飞（HELLO_ACK）用自己的**证书私钥**对握手 transcript 签名，终端用钉住的
  制造公钥验签 → 终端确认对面是"真模块"；伪造模块过不了（见 §3 T3 测试）。
- 帧头（magic/版本/类型/sessionId/seq）作为 **AEAD 的 AAD**，任何一位被改动都会失败。
- 序列号严格递增 + 跳跃上限，重放/乱序在解密前就被拒。
- **明确边界**：链路层只保证机密性、完整性和"活会话内的注入/重放防护"，**不把终端当作认证
  主体**——因为终端假设可能已被换。真正的出钞权在 §2.1 的主机签名里。

### 2.3 弱芯片上的现实约束（每条都是防御，不只是性能）

出钞模块控制器假设是 Cortex-M0+ 级：几十 KB RAM、无 MMU、非对称运算毫秒级、NVRAM 写入
寿命有限、时钟可被干扰。这些约束都被做成**强制预算**，否则就是攻击者的 DoS 杠杆：

| 预算 | 值 | 防的是 |
|------|----|--------|
| 单帧字节上限 | 4096 | 恶意超大帧撑爆解析内存 |
| 验签速率 | 8 次/秒 | 伪造签名洪水把 CPU 打死 |
| 握手速率 | 3 次/秒 | 每次握手要花模块一次签名 |
| NVRAM 提交/小时 | 600 | 反复触发写入磨损闪存 |
| 连续授权失败 | 20 次即锁定待维修 | 把模块当签名预言机 / 噪声源 |
| 挑战有效期 | 30 秒 | 过期 nonce 不得再用 |

### 2.4 离线：为什么不是"预算计数器"，而是"绝对累计上限"

朴素做法是主机发"你可以花 3000、最多 3 笔"，模块记剩余额度。**这个模型在芯片被读写的攻击
下是破的**：攻击者用编程器把 NVRAM 恢复到"额度满"即可重复套现。

本方案的修正：

- 主机签发的信封携带的是**绝对的终身累计上限**（`spendCapCents`、`txCountCap`），由主机
  根据上次对账得到的"该模块历史累计离线消费"加上本次授予额度算出。
- 模块维护两个**只增不减、OTP 锚定**的累计量：`cumulativeOfflineSpend`（分）和
  `cumulativeOfflineCount`。
- 出钞允许当且仅当 `cumulativeSpend + amount <= spendCap` 且 `cumulativeCount + 1 <= txCountCap`。

于是回滚 NVRAM **无法刷新额度**：OTP floor 把累计消费钉死，而签名上限是固定的。即使把旧信封
重放一遍，累计消费已顶在同一个绝对上限上，也只是被拒。

回滚的检测机制见 §2.5。

### 2.5 存储分层：NVRAM 不可信，OTP 是锚

- **NVRAM**（电池后备 SRAM）：只存储量数据（钞箱余量、审计日志窗口、最近回执哈希、
  累计值的镜像）。**假设其中每个字节都可被攻击者读写**。A/B 双缓冲抗掉电撕裂。
- **OTP**（一次性可编程 fuse）：可读、只能向前烧写一次。存放单调计数器、配对 epoch。
  这是"攻击者无法回滚"的唯一存储。
- **启动校验**：从 NVRAM 读回累计值/序高水位/epoch，与 **OTP floor** 比对。低于 floor 即判定
  回滚 → 锁死模块（`failClosed`），必须维修跳线才能恢复。OTP 烧满则拒绝在无锚状态下继续 → 同样失败关闭。
- **代价诚实说明**：OTP 烧写是稀缺资源。高频、低价值的状态不能放这里；只有离线出钞、重配对、
  epoch 变更这类**低频高价值**事件才消耗 OTP。这也是为什么"离线累计消费"用 OTP 锚定而"钞箱
  余量"只用 NVRAM。

### 2.6 回执与对账

每次成功出钞，模块用自己的私钥签发 `DispenseReceipt`，记录**实际**出钞计划，并：
- 携带 `moduleSeq`（严格递增）；
- 携带 `prevReceiptHash`（哈希链）；
- 绑定授权摘要（在线）或信封指纹（离线）。

主机在对账时验签、查哈希链、查重复结算、核离线信封额度。物理层面的钞箱短款则在库存结算里
体现——软件层能证明"哪些钱是经授权的"，盗走的现钞靠对账暴露。

### 2.7 维修重配对（T3）

`PairingGrant` 必须同时满足三道互相独立的门，缺一不可：

1. **主机服务授权签名**：只有银行服务密钥能签发，模块 OTP 钉住其公钥。
2. **物理维修跳线闭合**：远端攻击者无法满足。
3. **一次性 + 有效期**：授权 id 烧入 NVRAM，重复使用被拒；且绑定确切模块/终端/工单/技师。

成功重配对抬升 OTP 锚定的 epoch，并使旧 epoch 的一切授权/信封失效。重配对**不重置**出钞序号
高水位——主机分配的序号本就跨 epoch 单调，重置它会让合法的新授权被误拒。单个模块被攻破不
影响其他模块。

## 3. 黑盒攻击测试矩阵

`src/test/java/com/bank/atmsecure/attack/` 下每条测试都对应真实攻击能力，全部断言"钱没动"
（`cassettes` 计数不变）。测试**不**帮助攻击者——攻击者只拿到总线字节和公开接口，和真实焊线一样。

| 测试类 | 场景 | 期望 |
|--------|------|------|
| `BlackBoxBusAttackTest` (9) | 无签名伪造、真授权重放、密文翻转、帧头翻转、畸形/超大/截断帧、跨会话换帧、绕过终端手编帧、改模块 ID、总线明文泄露检查 | 全部拒绝 |
| `TerminalSwapAttackTest` (3) | 克隆终端篡改金额、克隆终端伪造主机签名、冒用他机身份 | 全部拒绝 |
| `ModulePairingAttackTest` (9) | 无跳线、无签名、跨模块授权、授权重放、epoch 不前进、重配对作废旧授权、换模块、单模块隔离、假模块证书 | 全部拒绝 |
| `OfflineAttackTest` (9) | 信封额度/笔数/单笔上限、重放信封、伪造信封、**NVRAM 回滚刷额度**、回滚锁死、掉电撕裂、回执对账 | 拒绝/锁定 |
| `ResourceAndFaultAttackTest` (6) | 伪造洪水限流后锁定、RNG 卡死关闭、过期授权、序号超前、nonce 单次用、物理盗钞对账 | 失败关闭 |
| `ImpersonationAndReplayAttackTest` (4) | 假模块握手、链路层重放/反射、序号回滚重放、旧会话 channelBinding | 全部拒绝 |
| `CrashConsistencyTest` (2) | 掉电不砖机、离线跨掉电不超额 | 单调不回滚 |
| `integration/*` (16) | 诚实路径、主机业务策略、审计链、生命周期回归 | 正常通过 |

**总计 69 个测试，全绿。**

> 注意 §6 的残余风险：软件能保证"只有被主机授权的交易才能出钞，且故障/回滚不会放款"，
> 但**不能**阻止攻击者物理搬走现钞，也不能防住主机/HSM 本身被攻破。

## 5. 如何运行

```bash
export JAVA_HOME=$(/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home)
gradle test        # 65 个测试
gradle run         # 攻击回放演示：每一步打印"被拒"和钞箱余额不变
```

`gradle run` 的输出依次演示：诚实基线 → 总线伪造 → 抓包重放 → 克隆终端 → 离线回滚 →
维修重配对。每一段攻击后钞箱计数保持不变。

## 6. 残余风险与明确不做的事（诚实交代）

安全设计必须说清楚"它不防什么"，否则就是虚假安全感。

1. **整模块被物理替换成攻击者控制的 MCU**：模块内的一切状态（OTP 也不例外）都在攻击者手里，
   模块内没有任何机制能防住。这一层的兜底在模块之外：(a) 主机的离线信封按 txId/回执链对账，
   重复或超额会被标记；(b) 物理现钞已经出去了，下一次库存结算必然暴露。**软件无法阻止物理
   拿走现金**，只能让它事后可审计、可定责。
2. **主机或 HSM 被攻破**：信任根被连根拔起，方案整体失效。这超出本组件范围，需要 HSM 自身的
   认证（FIPS/CC）与主机侧最小权限。
3. **供应链 / 出厂密钥泄露**：制造密钥泄露可造出假模块证书。需要出厂密钥在 HSM 内、可轮换，
   以及模块身份的多源核验（序列号、资产系统）。本模拟器只建模了密码学绑定。
4. **侧信道**：Ed25519 验签的时序侧信道、功耗分析未建模。真机需常数时间实现与屏蔽。
5. **时间**：模块 RTC 弱且可被干扰。本方案用时戳只做"宽限期"判断，真正的抗重放靠 nonce + 序号，
   不依赖时钟准确性。时钟被向后拨会落入确认窗口，但序号与 nonce 仍拦住重放。
6. **离线额度的根本权衡**：离线期间模块必须被信任去花掉一个上限。上限越小、有效期越短，
   T4 的最大损失越小，但离线可用性越差。这是业务决策，本设计只保证"回滚不能突破上限"。

## 7. 关键设计取舍速查

- 为什么不给终端任何签名权？——终端是假设会被换掉的那台 PC（T2）。
- 为什么签精确钞票计划而不只签金额？——防总额不变的面额替换。
- 为什么 nonce 由模块产生？——让授权与"这一次会话"绑定，抓包重放无效。
- 为什么离线用绝对累计上限？——预算计数器可被 NVRAM 回滚刷新，绝对上限不能。
- 为什么重配对不重置序号？——序号由主机跨 epoch 单调分配，重置会导致误拒或重放窗口。
- 为什么错误码粗？——细粒度失败原因本身就是一个攻击预言机，细节只进模块本地审计日志。
